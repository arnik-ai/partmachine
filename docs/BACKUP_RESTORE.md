# پشتیبان‌گیری و بازگردانی پارت‌ماشین

> مخاطب: کسی که سرور پارت‌ماشین را نگه می‌دارد. دستورها از ریشه‌ی مخزن روی سرور اجرا می‌شوند. برای کوتاهی، همه‌جا `dc` یعنی:
>
> ```bash
> docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.prod
> ```

## خلاصه

| چه چیزی | چطور |
|---|---|
| پایگاه داده | هر شب با `pg_dump` (همه‌ی جدول‌ها و داده‌ها) |
| فایل‌ها (نقشه، مدرک، تصویر) | هر شب، اگر روی دیسک سرور باشند (`STORAGE_BACKEND=local`). با فضای ابری S3، نگه‌داری فایل‌ها با خود آن سرویس است |
| زمان | یک بار هنگام بالا آمدن سرویس، و بعد هر شب ساعت ۳ بامداد تهران (`BACKUP_AT=23:30` به وقت UTC) |
| نگه‌داری | ۱۴ روز آخر (`BACKUP_KEEP_DAILY`)؛ قدیمی‌ترها خودکار پاک می‌شوند |
| رمزگذاری | همه‌چیز با `BACKUP_PASSWORD` رمزگذاری می‌شود (ابزار restic) |
| محل | پیش‌فرض روی همین سرور (volume `backups`). پیشنهاد: یک نسخه جدا از سرور (پایین‌تر) |
| هشدار | اگر بیش از ۲۶ ساعت پشتیبان موفقی ثبت نشود، به همه‌ی ادمین‌ها اعلان می‌رسد. `dc ps` هم سرویس `backup` را `unhealthy` نشان می‌دهد. تا وقتی مخزن روی همین سرور است، هفته‌ای یک بار یادآوری «پشتیبان‌ها فقط روی همین سرور نگه داشته می‌شوند» می‌آید (`partmachine_backup_offsite 0` در `/metrics`) |

## رمز پشتیبان: مهم‌ترین نکته

**بدون `BACKUP_PASSWORD` هیچ پشتیبانی قابل بازگردانی نیست، حتی برای خود ما.** آن را جایی بیرون از سرور هم نگه دارید، مثلاً در یک مدیر رمز. اگر سرور از بین برود و رمز فقط روی همان سرور بوده باشد، پشتیبان‌ها هم بی‌فایده‌اند.

## نسخه‌ی جدا از سرور (پیشنهادی)

پشتیبانِ روی همان سرور در برابر اشتباه انسانی و خرابی نرم‌افزار کمک می‌کند، ولی اگر خود سرور از دست برود، از دست می‌رود. برای نسخه‌ی جدا، مخزن را روی یک فضای S3-سازگار جدا (مثلاً یک bucket دیگر در لیارا یا ابر آروان) بگذارید:

```bash
# در deploy/.env.prod
BACKUP_REPOSITORY=s3:https://storage.example.ir/partmachine-backups
BACKUP_S3_ACCESS_KEY_ID=...
BACKUP_S3_SECRET_ACCESS_KEY=...
```

بعد `dc up -d backup`. اگر میزبان هم پشتیبان خودکار از کل سرور دارد، آن را هم روشن کنید (S8).

## کارهای روزمره

```bash
dc exec backup partmachine-backup list    # فهرست پشتیبان‌ها با زمان
dc exec backup partmachine-backup run     # همین حالا یک پشتیبان، مثلاً پیش از یک تغییر بزرگ
dc logs --tail=50 backup                  # گزارش آخرین پشتیبان‌ها
```

## بازگردانی

بازگردانی پایگاه داده و فایل‌های فعلی را **کامل جایگزین** می‌کند. برای همین بدون `--yes` اجرا نمی‌شود.

```bash
dc stop api worker                                      # ۱. کسی در این فاصله چیزی ننویسد
dc exec backup partmachine-backup restore --yes         # ۲. آخرین پشتیبان
#   یا یک پشتیبان مشخص: restore --yes <شناسه از list>
dc start api worker                                     # ۳. برگشت سایت
```

سپس سایت را باز کنید، وارد شوید و چند سفارش و فایل را نگاه کنید.

فایل‌ها از **همان نوبت پشتیبانی** برمی‌گردند که پایگاه داده از آن آمده است (برچسب مشترک `run-…`)، تا پایگاه داده و فایل‌ها مال یک لحظه باشند. پشتیبان‌هایی که پیش از ۲۰۲۶/۱۰/۲۷ گرفته شده‌اند این برچسب را ندارند؛ برای آن‌ها، با هشدار در لاگ، آخرین پشتیبانِ فایل برمی‌گردد.

### روی سرور تازه (وقتی سرور قبلی از دست رفته است)

1. مخزن را بگیرید و `deploy/.env.prod` را با **همان** `BACKUP_PASSWORD` و `BACKUP_REPOSITORY` بسازید. رمزهای دیگر می‌توانند تازه باشند.
2. `dc up -d --build` و بعد مراحل بازگردانی بالا.

## تمرین بازگردانی

یک تمرین کامل با هر تغییر در CI اجرا می‌شود (job `production-stack`):

1. یک حساب واقعی ساخته می‌شود.
2. پشتیبان گرفته می‌شود.
3. پایگاه داده کامل پاک می‌شود و بررسی می‌شود که هیچ جدولی نمانده باشد.
4. پشتیبان بازگردانده می‌شود.
5. سایت دوباره بالا می‌آید و همان حساب دوباره پیدا می‌شود.

زمان پشتیبان و بازگردانی در خلاصه‌ی همان اجرای CI ثبت می‌شود.

| تاریخ | جا | حجم داده | پشتیبان | بازگردانی |
|---|---|---|---|---|
| ۲۰۲۶/۱۰/۱۵ (۲۳ مهر ۱۴۰۵) | GitHub Actions (ubuntu-latest) | پایگاه داده‌ی آزمایشی، ۹۲ کیلوبایت (۱۴ کیلوبایت پس از فشرده‌سازی) | ۲ ثانیه | ۲ ثانیه |

زمان واقعی با حجم داده بالا می‌رود. پس از راه‌اندازی، همین جدول را با نتیجه‌ی تمرین روی سرور واقعی کامل کنید.

روی سرور واقعی هم ماهی یک بار همین تمرین را روی یک کپی انجام دهید.
